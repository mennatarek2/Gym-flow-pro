Not an accounting module

Member 360 stays a person page. Outstanding is one financial fact: how much this member still owes on real sales.

Collect Payment uses POST /api/sales/{id}/payments — the same write path POS already has. There is no separate debt payment.

Verdict: READY FOR IMPLEMENTATION

Option B — Outstanding derived from Sales / Payments. Do not add Member.DebtAmount. Do not restore a Debtors desk. First implement pass needs one read API (outstanding sales for a member) plus the Collect Payment drawer.

What already exists

Remaining lives on Sale.AmountDue. Member total = sum of that member’s partially_paid sales. Follow-on pay is already POST /api/sales/{id}/payments. Dashboard KPI and Member 360 already show the total. POS can create a partial sale; it cannot collect an old one (removed on purpose).
Member → Sale (AmountDue) → PaymentTransaction Outstanding = SUM(AmountDue) where status = partially_paid

Collect (proposed)

Member 360 → Collect Payment → pick one sale → method + amount → POST /sales/{id}/payments → refresh Outstanding

Pay one sale, not auto-allocate

The write API is per-sale. Auto-splitting one cash take across many tickets would be a new allocator. v1 is Option A: receptionist chooses the ticket.

Language

Outstanding · Amount due · Remaining · Collect Payment. Not Debtor, AR, aging, write-off.
